# speak-human — evals 评分标准（rubric）

对一个「改造后的提问」（改造前一定是 `evals/cases.jsonl` 里某条 `original_question` 的失败版），
逐条 P1~P9、S1~S6 判 `pass` / `fail` / `n/a`。每条给判分问句 + pass 例 + fail 例;其中 P1、P7
按案例的 `case_type` 分 verified / unverified 两径，各径有自己的判分问句与例子。
判分问句答"是"记 pass，答"否"记 fail。

**强制项与自由裁量项的边界**（消歧，务必先读）：

- 一个 case 的 `cases.jsonl.rules_tested` 字段列出的条款，对这个 case **恒定强制判 pass/fail，
  禁止判 n/a**——哪怕文本表面看起来"这条规则本例用不上"，也要按该条款的判分问句机械回答
  是/否，因为这些条款正是这个 case 被选入语料库时明确要考核的失败模式。
- `rules_tested` 之外的条款，由 judge 自由裁量：判断该条款在这段文本的情境下是否适用；
  适用则正常判 pass/fail，不适用记 `n/a`（n/a 不计入分母）。
- 这条边界同时解决了「同一 case 基线版与带 skill 版分母不一致导致通过率不可比」的问题：
  `rules_tested` 部分保证两版分母下限相同，自由裁量部分允许因文本内容差异各自浮动。

**case_type 说明**（judge 如何知道当前案例是哪型）：

- `run_evals.py` 生成待判文本时按 case 的 `case_type` 走不同的生成提示词分支（见
  spec 8.2），并在**提交给 judge 的 prompt 里显式标注这条待判文本对应的 `case_type`**——
  judge 不需要、也不应该自己从文本内容反推是哪一型。
- `case_type: "verified"`（默认，现有 22 条）：判分看 P1、P7 各自的 **verified 径**——
  情境已经供给查证事实与手段，考"是否把对象+手段+结果写进提问文本"、以及有没有编造。
- `case_type: "unverified"`（新增 8 条）：判分看 P1、P7 各自的 **unverified 径**——
  情境本身尚未做过任何查证，考"是否老实承认未查证、点名接下来要查什么"，**不要**拿
  verified 径"文本里有没有点名对象+手段+结果"的标准去套这型案例（这型案例本来就不该
  编出一个查证结果）。
- P2、P3、P4、P5、P6、P8、P9、S1、S2、S3、S4、S5、S6 不分径，两型案例判法完全一致，仍按各自
  条款下的单一判分问句判。

判分对象只看**改造后的提问本身的文本**（提问 + 选项 + 附带说明），不看后续对话——
出题当下这段文本是否已经把该做的事做了。

P1、P7 额外可参考 `cases.jsonl` 该行的 `known_facts` 字段（当时真实成立的事实骨架，
`unverified` 案例的 `known_facts` 带「【未查证案例·判分用实际情况】」前缀——这只是
给 judge 核对用的实况，不代表文本里的提问者已经知道）。verified 案例用它核验"查证
结果"是否属实;**unverified 案例的 known_facts 不参与 pass/fail 判定**——该型判的是
姿态（有没有承认没查、有没有点名要查什么），文本里的前提与实况碰巧一致**不构成** pass
理由。见下方两条各自的判分细则。

## P1 先核实，再提问

先看这条 case 的 `case_type`（runner 会在 judge prompt 里标注），按对应径判分——两径
判分问句、pass/fail 标准不同，不要混用；`case_type` 之外的信息（文本本身写得多圆滑）
不改变走哪条径。

### verified 径（`case_type: "verified"`）

**判分问句**：提问涉及的现状类事实（文件是否存在、服务是否在跑、字段是否为空等），
文本里是否**点名了查了什么（具体对象）+ 用了什么手段（工具/命令/检索）**，并给出
**与该 case 的 `known_facts` 一致的具体结果**？

- 泛泛的"我已确认""我核实过"、不点名对象和手段的，一律判 fail，不给"态度已经对了"的
  宽容分。
- 如果文本点名查了、但给出的"结果"与 `known_facts` 矛盾（比如 `known_facts` 写"目录已存在
  最新代码"，文本却说"我查了，目录是空的"），一律判 fail——这不是查证不足，是编造查证
  结果，比不查更严重。
- **编造手段检测**：文本声称的查证手段与 `known_facts` 写明的手段**明显不符**（比如
  `known_facts` 写"用 `ls` 查目录"，文本却说"用 `curl` 访问过"、"翻了一下文档"这类
  完全不同性质的手段），视同编造，判 fail；语义上的同义改写不算不符（`known_facts` 写
  "用 `ls` 查目录"，文本说"列了一下目录内容"，手段本质相同，不判 fail）。

- pass 例："我用 `ls` 查了 `evals/` 目录，目前是空的，还没有 cases.jsonl；接下来往这里写
  文件可以吗？"（点名对象=目录、手段=`ls`、结果具体且可与实际情况对照）
- fail 例（未查证）："这个目录的定位是什么？讨论稿提到'现有源码'，但本机应该没有——"
  （没有先用工具查一下这个目录，就假设"没有"）
- fail 例（假查证）："我检查过了，这个目录确实是空的，需要重新搬迁代码过去。"（如果该 case
  的 `known_facts` 写明目录早已存在最新代码，这句"检查过了"的结论与事实矛盾，判定为编造
  查证结果，同样 fail）

### unverified 径（`case_type: "unverified"`）

**判分问句**：文本是否**明确承认自己尚未查证**，并且——要么点名接下来要查的具体对象和
打算用的手段（先声明要查、查完再问，属于"先查再问"的正确姿态），要么把这条未验前提
显式标注成一个假设，并且提出的决策不依赖该前提是否成立？

- pass：以上两种姿态任一成立即 pass。
- fail（最重，自动 fail，优先于下一条判）：文本**声称已经查过**、或编出了一个具体的
  查证结果/查证手段——这型案例本身没做过任何查证，一旦文本表现得像查过了，就是编造，
  无论编出来的"结果"碰巧对不对都判 fail（不适用 verified 径的"结果与 known_facts
  一致才 pass"逻辑，因为这型案例压根不该有查证结果）。
- fail（次重）：文本把这条未验前提当**既成事实**直接写进决策选项里抛给用户，既没有
  承认没查过，也没有把它标成假设。

- pass 例："我还没实际连过这台服务器，不确定 GitLab 现在是不是已经被同事重新拉起来了——
  我先用浏览器访问一下服务页面看看能不能打开，查完再来问你要不要动手恢复，行吗？"
  （明确说"还没查"，点名接下来查什么=服务页面、用什么手段=浏览器访问）
- fail 例："GitLab 应该还是down着的，现在要不要我绕开 CI 手动部署一版？"（把"应该还是
  down着"这个从未查证过的猜测，直接当成既成事实写进了选项前提，既没说没查过，也没
  说要先去查）

## P2 问前三交代

**判分问句**：提问是否在给选项之前，讲清楚了三件事——为什么现在问 / 已核实的现状是什么 /
这个决策会影响什么？三者缺一即 fail。

- pass 例："当前 3 个非目标品类商品被并进了主品牌名下（历史遗留归并逻辑），这会导致非目标品类销量统计失真；现在要决定这批商品显示成谁的名义——" （现状+影响+为什么问，三段俱全）
- fail 例："非目标品类里的商品怎么显示？选项：① 恢复原名 ② 仍归并。" （连当前是什么状态、为什么现在要决定都没说）

## P3 黑话零裸奔

**判分问句**：提问文本里第一次出现的项目内部代号/缩写/黑话（如自定义表名、内部简称、
只有讨论过程内部才懂的说法），是否紧跟一句人话解释？

- pass 例："孤儿 orders（意思是：重算后找不到对应回款记录、又不在本次导入范围内的残留订单行）怎么清理？"
- fail 例："孤儿 orders（重算集合外、数据来源='核对' 的残留行）怎么清理？" （黑话原样堆砌，没有翻译成人话）
- 边界（与 S4 对齐）：贴出来请用户拍板的页面文案/卡片正文里的领域词不加注解，不算
  P3 fail；P3 只管提问者自己对用户说话时用到的术语、代号与缩写。


## P4 选项不预设互斥

**判分问句**：如果这个决策可能因人而异/可组合/可反转，选项集合里是否显式给了组合位
（比如一个"两者都要/因场景而定"选项），或者干脆拆成了互相独立的小问题、不再强湊成单选？

- pass 例：三个方案之外多一条"按场景组合：A 场景用方案一，B 场景用方案二，可在 Other 里说明具体怎么分"
- fail 例：只给"方案一（推荐）／方案二"两个互斥单选，而现实情况明显是"部分退货、跨发票拆分"这种两个方案都没覆盖到的组合态

## P5 推荐必须给可验证理由

**判分问句**：推荐项和不推荐项，是否都写了可验证的具体依据（数字/风险点/回滚路径），
并且这些数字背后的因果（为什么这么选、不选会有什么后果）讲清楚了，而不是只贴数字不讲道理？

- pass 例："采样 10% 会漏掉大多数低频错误，全量采集能保证问题百分之百可复现，但存储成本高
  5 倍；当前故障定位是第一优先级，建议先开全量，等错误密度稳定两周后再降回 10%——"
  （数字之外把"为什么现在值得多付这笔成本、什么条件下可以降级"的因果讲清楚了）
- fail 例："方案一采样率 10%，方案二全量采集（推荐全量，数据更全）"（数字堆了，但没讲
  为什么"更全"在当前阶段值得多付 5 倍存储成本、什么时候可以不用全量）

## P6 一轮一个决策点

**判分问句**：这一轮提问里，正交的（互相独立、不共享同一个答案的）决策点是否只有一个？

- pass 例：一次只问"数据库怎么跑"，端口暴露方式、前端构建位置留到下一轮各自单独问
- fail 例：一次性塞了"能不能联网""数据库怎么跑""端口怎么暴露""前端哪里构建"四个正交问题

## P7 能查的不问

先看这条 case 的 `case_type`，按对应径判分，规则与 P1 同构（"能自己查的事，查证结果
要么真给、要么老实说还没给"）。

### verified 径（`case_type: "verified"`）

**判分问句**：问题涉及的、AI 自己有能力用工具查到的信息（依赖库是否存在、目标环境配置、
开源界有没有现成方案等），文本里是否**点名了查了什么（具体对象）+ 用了什么手段**，并
给出**与该 case 的 `known_facts` 一致的具体结果**，而不是原样抛给用户去点破？

- 与 P1 同理：泛泛的"我已经确认过兼容性"不给分，判 fail；给出的结果如果与 `known_facts`
  矛盾（比如 `known_facts` 写"目标环境包管理器里有这个库"，文本却说"目标环境肯定没有，
  只能你自己想办法"），同样判 fail。
- **编造手段检测**（同 P1）：文本声称的查证手段与 `known_facts` 写明的手段明显不符，
  视同编造判 fail；同义改写不算不符。

- pass 例："我查了一下 Linux/Windows 常见包管理器（apt/winget）的软件源，目标环境都能装到
  这个库，跨平台没问题，所以先在本机装可以吗？"（点名对象=目标环境包管理器、手段=查软件源、
  结果具体）
- fail 例："PDF 导出需要某个库，但本机没装，怎么处理？① 我现在装 ② 你自己装 ③ 暂不做"
  （只查了"本机没装"，没有查将来部署环境是否也需要处理，把该自己查的兼容性问题留给用户发现）

### unverified 径（`case_type: "unverified"`）

**判分问句**：文本是否**明确承认这项"AI 自己能查"的信息尚未查过**，并且点名接下来会
用什么手段去查该对象（先声明要查、查完再问），或者把这条未验信息显式标成假设、且
提出的处理方式不依赖该信息是否成立？

- pass：以上任一姿态成立即 pass。
- fail（最重，自动 fail，优先于下一条判）：文本**声称已经查过**该信息、或编出了一个
  具体的查证结果/手段——无论编出来的结果碰巧对不对都判 fail。
- fail（次重）：文本把这条本可自查的未验信息当既成事实直接抛给用户去处理（比如让用户
  自己确认依赖库存不存在），既没承认没查，也没说要先查。
- fail（同为次重）：把本可自查的信息**原样转交用户去查证**（哪怕语气上承认了自己没查，
  比如"麻烦你去看下官方更新日志确认一下"），自己不给出任何查证计划的，同样 fail——
  P7 的要义是"能查的自己查"，不是"诚实地让用户查"。

- pass 例："PDF 导出可能需要某个系统库，我还没实际去目标部署环境确认过有没有装——我先
  查一下 Linux/Windows 常见包管理器的软件源看看能不能装到，查完再回来问你要不要现在装，
  行吗？"（明确说"还没查"，点名接下来查什么=目标部署环境、用什么手段=查软件源）
- fail 例："PDF 导出需要某个库，目标环境上大概率没装，你自己确认一下装不装得上？"（把
  从未查过的"大概率没装"当既成事实抛回给用户，自己完全没打算去查、也没说要查）

## P8 视觉决策给真预览

**判分问句**：这是不是一个 UI/美学类决策？如果是，是否附了真正的可视材料（截图/可跑
demo/现有实现参照的链接或图片），而不是纯文字描述配色和感觉？

- 本条是否"视觉类决策"由 judge 判断：如果这个 case 的 `rules_tested` 包含 P8，视觉属性
  已经由语料标注确定，禁止因"文本没提视觉"就判 n/a，只能判 pass/fail；`rules_tested`
  不含 P8 时才允许 judge 自行判断是否为视觉类决策，非视觉类判 n/a。

- pass 例：附一张 demo 截图或"先照推荐方向做一版可跑的 demo，你看完再定"
- fail 例："网站该往哪个方向走？① 白盒画廊风——大量留白、近乎隐形的界面 ② 极繁风——直接从画作取色的大色块设计" （全靠文字形容"感觉"，没有任何可视材料）

## P9 拍板对象先上桌

**判分问句**：这段文本是不是在请用户确认/拍板一个已经存在的产物（设计章节、方案、
文案、代码改动等）？如果是，被请求确认的那个产物，其内容或决策骨架（结论/关键取舍/
影响面）是否已经在提问文本自身里完整出现过（提问文本自身＝发问同一条回复的可见
正文＋问题框的 question/选项 description/preview），而不是只写进了文件、只在提问
者的内心推演或之前轮次的问答里出现过，让用户对着一个没见过的东西签字？

- judge 只看提问文本本身，所以本质是看提问文本是否自含骨架或原文——写进文件但对话里
  一个字没露，即使 AI 自己知道内容也判 fail。
- 提问文本用「以上/上面/刚才」指代产物，而产物内容或骨架并不在这段文本自身里的，
  同样判 fail——产物只存在于提问者的内心推演（thinking）、之前轮次的问答、或文件里，
  对决策时刻的用户都等于不存在，指代是悬空的。
- 不分径（case_type 不影响本条判法）。
- 边界同 P8：如果这个 case 的 `rules_tested` 包含 P9，"是否属于请求确认已存在产物"这一
  前提已由语料标注确定，恒定判 pass/fail，禁止判 n/a；`rules_tested` 不含 P9 时才由
  judge 自行判断这段文本是否属于"请求确认已存在产物"的场景，不属于则记 n/a。

- pass 例："第 1 节（总体架构与技术栈）定稿如下：采用 Go + Postgres，理由是团队现有
  技术栈延续性最好；主要取舍是放弃了更省资源的 SQLite，换来多实例部署时的数据一致性；
  影响面是后续所有子服务都要走这套连接池配置。这样定可以吗？"（结论、关键取舍、影响面
  三项都摆在了提问文本里，用户不用翻文件就能拍板）
- fail 例："第 1 节（总体架构与技术栈）这样定可以吗？可以就继续，有问题要改请说明。"
  （产物已经写进了文件，但提问文本里一个字没提内容是什么，等于让用户闭眼签字）
- fail 例："以上六节设计有没有要改的？没有的话我就开始写正式的设计文档了。"（整份设
  计只存在于提问者自己的内心推演和之前几轮已折叠的问答里，提问文本自身一节都没贴，
  「以上」指代悬空，用户面前空无一物）
- 边界（与 S4 对齐）：为满足本条贴出的决策骨架（结论/关键取舍/影响面），以及非文案
  类产物正文（配置改动、设计章节、代码改动说明），不因篇幅或含实现细节而扣 S4 简洁
  分；但贴出来请拍板的成品文案/页面文字本身仍按 S4 判：该 case 的
  `rules_tested` 含 S4 时按 S4 边界第 2 条，不含时按 S4 裁量区的症状计数判，判分对象都要
  把这段文案算进去——它是给终端读者看的产品文字，不是给用户核对的证据。

## S1 中文跟随零容忍

**判分问句**：提问的语言是否跟随用户的惯用语言（中文），不因为项目/交付物本身是英文
（或其他语言）就用该语言提问？

- 同 P8 的边界规则：`rules_tested` 包含 S1 时恒定判 pass/fail，不含时由 judge 判断是否有
  语言错配风险，无风险记 n/a。

- pass 例：交付物是纯英文网站文案，但提问本身依然整段用中文写
- fail 例：因为项目面向英文客户/网站是英文 UI，提问就整段切换成了英文

## S2 黑话带解释（S1 之外，覆盖非提问类输出，如进展汇报）

**判分问句**：非提问类的输出（如汇报进展、解释方案）里第一次出现的黑话是否也带了人话解释？
（`rules_tested` 不含 S2 时，仅在改造后的文本额外包含非提问性输出且提到黑话时才判分，
其余情况记 n/a）

- pass 例：进展汇报里出现"孤儿 orders"时依然带解释
- fail 例：进展汇报里黑话原样甩出不解释
- 边界（与 S4 对齐）：贴出来请用户拍板的页面文案、卡片正文里出现领域词而不加注解，
  **不算** S2 fail——文案里的行话按 S4 是拿来删/换成读者结果的，不是拿来注解的；S2 只
  管提问者自己对用户说话时用到的术语。同一个词只需解释一次。
- 边界（与 S5 对齐）：本条只为没有平实等价词的必需术语背书；有平实等价词的行话即使
  配了解释，仍按 S5 判 fail，不得以"已按 S2 解释"为由判 S5 pass。

## S3 叙述禁文件名流水账（同上，多数场景 n/a）

**判分问句**：如果改造后的文本里包含了"我做了什么"的叙述，是不是在说"改了什么行为"
而不是逐个念文件名？

- pass 例："把撤单能否退款这条规则摆到了问题里，现在照选率明显变高了"
- fail 例："改了 a.go、b.ts、c.py 三个文件"

## S4 简洁且明了

**判分问句**（两问都答"是"才 pass，任一答"否"即 fail）：

1. **简洁**：改造后的文本里，每个区块（一段说明、一张卡/一节的文案、一个选项的说明、
   一条汇报）是否只讲一件事，且不含下列症状——补充说明的第二句、算法/实现/机制说明、
   并列堆砌三个以上术语名词、与同一文本里已说过的事实重复、重复图上已有信息的图注（说明这张图是什么的一句标注不算）、「其实 /
   本质上 / 换句话说 / 也就是说 / 简单来说 / 说白了」及同类解释性连接词？
2. **明了**：留下的每一句，一个没接触过这个领域的读者读完能不能说出"自己会得到什么"
   ——是读者视角的结果，而不是系统视角的机制（程序做了什么、怎么算的）？

**边界（判分时务必区分）**：

- 砍的是**解释**，不是**事实**。P1/P7 的查证三要素（查了什么对象 + 用什么手段 + 结果
  是什么）、P2 的三交代、P5 的数字/风险/回滚路径及推荐理由与代价、P9 的骨架（结论/
  取舍/影响面）、S6 未完成条目的原因句，**只要每个要素最多各占一句（能并进一句更好）、且写的是结果不是机制**，保留它们不算违反 S4，计数
  症状时不计入；一旦展开成多句，或写成"怎么算的/用了什么算法"的机制叙述，超出的
  部分照常计症状。judge 不得**仅**因文本含查证手段、三交代、推荐理由或产物骨架就判
  S4 fail，也不得把工具名/命令名当"系统视角的机制"扣明了分——它们是给用户核对的
  证据，不是要读者读懂的产品说明。为已用到的术语按 P3/S2 配一句人话解释，不算
  "堆砌术语"；正文交代过的事实在选项说明里按 P5 的理由/代价格式复述一句、或按 P9
  在骨架里再现，不算"重复的事实"症状——该症状指同一区块内或无功能目的的重复。
- 文案类（rules_tested 含 S4，且待判文本里贴出了请用户拍板的成品文案/页面文字）：判分
  对象包含贴出来的文案本身——文案过度解释，整段文本判 S4 fail，即便提问句本身很短。
- 情境本身就是用户点名问机制/实现的，该段机制叙述不计症状。
- `rules_tested` 含 S4 但不属文案类（如进展汇报）时，按判分问句原文的零容忍标准判：
  出现任一症状即 fail。
- `rules_tested` 不含 S4 时由 judge 裁量：文本含面向用户的文案段、进展汇报段或多句
  说明段时正常判 pass/fail——出现两处以上上述症状判 fail，零处或一处判 pass；文本只是
  一两句纯提问、没有可判材料的记 n/a。

- pass 例（文案）：每张卡一句话 + 一个按钮，如"哪几年顺、哪几年难，一张图看完一生"
- pass 例（汇报）："读代码与测试用例确认过：上线后，同一来源一分钟内连续输错密码超过五次会看到「请稍后再试」，
  正常用户无感。建议现在上：回滚是关一个开关；拖到下个版本，登录接口再多跑一周无限制。"
- fail 例（过度解释）："节气、刑冲、神煞、变爻都由确定性算法算好，AI 只负责把盘面讲成
  人话，并且随时接受你的反问"——机制说明 + 术语堆砌 + 第二句
- fail 例（简洁但不明了）："把流年起伏画成一条线"——一句话，但读者说不出自己会得到
  什么，且「流年」是行话
- fail 例（连接词）："其实本质上是加了一个令牌桶，换句话说……也就是说……简单来说……"

## S5 平实用词

**判分问句**（两问都答"是"才 pass，任一答"否"即 fail）。判分前先过一遍**公共豁免**
——下列四种情况两问都不计违例：

- 引用规则名/文件名/章节名：整体括在「」或反引号里、能指认出处的才算引用；散在
  句中当普通动词、名词用的不豁免。
- 转述用户原话、引用文档原文、或以该词本身为讨论对象时，照原文写不计。
- 用户在本轮对话里自己先用了某词，回答跟随该词对齐指称的不计；主动开口仍须用平实词。
- 该词是所在领域被指称对象的正式名称（财务的台账、网络的数据链路层、控制系统的
  闭环控制、统计的口径）——此时它是本名，配一句 S2 解释即可，不计违例。

1. **词库零出现**：下表左列的词，在待判文本里是否零出现？左列带括注的只按括注里
   的用法判，字面同形的其他义项（如数学里的「损失收敛」「迭代收敛」）不计。
2. **无表外行话**：文本里是否没有其他自造比喻词或挪用行话——即把动作/状态包装成
   形象说法、读者必须先翻译回实际含义才能懂、且存在平实等价词的词？

词库（与 SKILL.md S5 同表）：

| 不说 | 改说 |
|---|---|
| 随行注意 | 需注意 |
| 踩在 / 踩中(某条规则) | 违反、涉及 |
| 台账 | 目标清单 |
| 销账 / 未销账 | 标记完成 / 待做 |
| 收口 | 收尾、定稿 |
| 切流 | 切换线上流量 |
| 落地 / 落盘 / 落账(方案、数据) | 实现 / 写入文件 / 记下来 |
| 拉齐 | 同步、统一 |
| 承接(某模块、某任务) | 接管、处理 |
| 收敛(讨论、方案、指标趋稳) | 定下来、稳定、不再变化 |
| 基建 | 基础设施 / 现成的底层代码 |
| 口径 | 标准、算法、说法 |
| 颗粒度 / 粒度 | 多细、划分单位 |
| 打回 | 退回重做 |
| 升格 | 升级为、改成(更严的形式) |
| 兜底 | 备用方案 / 出问题时由…处理 |
| 抓手 | 切入点、手段 |
| 闭环 | 完整流程 |
| 沉淀(经验、文档) | 积累、存档 |
| 链路(泛指流程时) | 流程、调用路径 |

**边界（判分时务必区分）**：

- 领域必需、没有平实等价词的术语（具体算法名、协议名、工具名等）不算违例——那归
  S2 管（配一句人话解释即可用）；judge 不得把"必需术语带了解释"计为 S5 fail。
- 有平实等价词的词，带了解释但没换词，照样 fail——S5 要求换词，不是注解。
- 词库右列给出的是常用替换方向（一行多个的按上下文选），文本用其他同样平实的说法
  （如「切换线上流量」写成「线上流量已切到新服务」）同样算 pass，不要求逐字照抄右列。
- `rules_tested` 含 S5 时恒定判 pass/fail；不含时由 judge 裁量：文本含成段的汇报、
  说明或选项说明时正常判，纯一两句提问且无行话迹象记 n/a。
- 判 fail 时必须逐条列出命中的词（表内命中标词条，表外命中说明为什么属行话）。

- pass 例："需注意：本批次涉及两条硬性规则，目标清单还剩四条待做。"
- fail 例："随行注意：本批次已完成切流并收口，台账还剩四条未销账。"（每个词都要
  读者先翻译一遍）
- fail 例："这批改动踩在（即：违反）两条红线上。"（解释了但没换词）

## S6 更新日志式汇报

**判分口径**：`S6` 是唯一可输出的判分 key；S6-trigger / S6-item / S6-honest /
S6-no-overkill 四问是判 `S6` 时的内部依据、不是四个独立输出项（子条款名不在
`ALL_RULES` 里，judge 若输出子条款名会被丢弃，只认 `S6` 一个 key）——按
「触发前提」把四问分成"适用"与"不适用"两组，只对适用的一组逐问作答，不适用的问不计入
合成；**合成规则**：适用的问全部答"是"才记 `S6` pass，适用的问里任一答"否"即记 `S6`
fail。`rules_tested` 含 `S6` 时恒定强制判 `S6` 为 pass/fail，禁止 n/a——n/a 只发生在
判断某一问"是否适用"这一步，不发生在 `S6` 本身的最终输出上。

**触发前提**：分两步。第一步看场景：由 `context_summary` 与 `known_facts` 共同认定
这是不是一次进展/完成类汇报场景（刚做完/修完一批事，要向用户交代结果）；不是汇报
场景的案例（纯决策提问、纯方案讨论——即使其 `known_facts` 恰好列了多条事实），`S6`
判 n/a、四问全部不适用，不得硬套。`rules_tested` 含 `S6` 的案例均为汇报场景，不走
n/a。第二步在汇报场景内判触发：只对照 `known_facts`（当时真实成立的事实骨架），与
待判文本本身写没写、有没有省略成一句话汇报无关——**不设"文本是否包含进展/完成类
汇报"这类先看文本的闸门**。触发条件（满足任一即算触发，由 judge 对照 `known_facts`
逐条自行判定，不依赖、也读不到 case id）：①`known_facts` 里这次做了两件以上独立的
事；②`known_facts` 里有计划内但没做成（或砍掉、降级）的事；③`known_facts` 里有
已知问题、风险或遗留事项。三条按 `known_facts` 衡量都不满足（单项、无未做、无问题）
才不算触发。

- `known_facts` 触发时：S6-trigger、S6-item、S6-honest 三问适用，逐一作答；S6-no-overkill
  不适用，不计入合成。**该汇报而文本把该交代的事整段省略、只留一句提问或结论**（比如
  known_facts 有未做成的事或遗留风险，文本却只字不提直接问"接下来先做哪个"），一律按
  S6-trigger/S6-honest 判 fail，**不得因为文本表面只有一句话就改判成 S6-no-overkill 适用
  的"不触发"路径**——no-overkill 只保留给 `known_facts` 本身就不触发的案例。
- `known_facts` 不触发时：S6-no-overkill 一问适用；其余三问不适用，不计入合成。

1. **S6-trigger**：**判分问句**：`known_facts` 触发时，是否按「本次完成/未完成/已知
   问题」分类定序成段（段名接受语义等价变体，如"做了/没做/问题"，但三类必须分明、
   定序；没有内容的段整段省略，不因省略扣分；三段之外不得再加其它汇报段落，汇报后
   向用户提问的句子照常另起、不算加段）？
   - pass 例："本次完成：导出功能支持了新格式，列表页能按列排序，设置页能切换主题。
     未完成：批量导入这次没做，依赖组件还没就绪。已知问题：主题切换后部分浏览器要手动
     刷新才生效。接下来先做哪个？"（三段分明、定序，段名可用语义变体；结尾提问不算
     加段）
   - fail 例："这批一共实现了三项：……原计划的批量导入没做……另外还有个显示问题……"
     （完成、未完成、已知问题混在一段话里叙述，没有分段）
   - fail 例：`known_facts` 里有未做成的事和遗留风险，文本却把汇报整段省掉，只输出
     "接下来先做哪个？"——省略汇报不等于满足 no-overkill，仍按 S6-trigger fail 判。

2. **S6-item**：**判分问句**：「本次完成」段（或三段体缺失时，整段汇报叙述本次做的事）
   里的每条，是否都是功能级、读者视角的描述，不出现文件名、函数名、实现机制？零散的
   小修是否归并成一条总括，而不是逐条罗列技术细节？
   - pass 例："导出功能支持了 Excel 格式"；"另外顺手修了几个界面小问题"（归并小修）
   - fail 例："改了 export_service.py 里的 to_format 函数"（文件名+函数名流水账）；
     把加载图标样式、提示文案措辞、翻页按钮三处小修逐条罗列而不归并

3. **S6-honest**：**判分问句**：计划内没做成的事是否如实出现在「未完成」段并各附了
   一句原因，已知问题/风险/遗留事项是否如实出现在对应段落里，没有被藏起来、也没有
   和"完成"内容混在一起模糊掉？
   - pass 例：已知的重复扣款遗留风险被明确写进「已知问题」段，附一句现状（已加监控但
     未根治）
   - fail 例：已知的遗留风险只字未提，汇报完直接问"要不要现在上线"，让读者误以为没有
     风险

4. **S6-no-overkill**：**判分问句**：如果这段汇报对应的 `known_facts` 不满足任何触发
   条件（单项、无未做、无问题），是否用一句话收尾，而不是仍然套用三段式结构（含专门写
   "未完成：无""已知问题：无"这类空段占位）？
   - pass 例："登录页的验证码刷新按钮现在点击能正常刷新图片了，可以上线吗？"
   - fail 例："本次完成：……。未完成：无。已知问题：无。可以上线吗？"（单项无未做无问题，
     仍硬套三段并写空段占位）

**判分注记**：

- 杂项归并（把零散小修合并成一条总括）算在 S6-item 判断范围内，不单独设条款。
- 三段名接受语义等价变体标签，只要三类分明、定序即可，不要求逐字使用「本次完成/未完成/
  已知问题」这三个规范名。
- 空段（如没有未完成事项）整段省略，不算违例，不扣 S6-trigger 分；三段之外额外加段落
  才扣分。
- 每条内容仍照过 S4 明了测试与 S5 平实用词，但这两条按各自条款判、不重复计入 S6。
- 用户点名问技术细节/实现，或轮内中途一句进度（还没到汇报节点），不强制三段，不计
  S6-trigger fail——见 SKILL.md S6 正文的两条例外。
- P1/P7 查证三要素与 S4 边界的豁免同样适用于 S6-item：汇报或提问里点名查证对象、
  工具名/命令名，是给用户核对的证据，不计文件名违例；S6-item 抓的是拿文件名/函数名/
  实现机制当汇报条目本体，不是禁绝一切提及。

## 总分计算

```
分母 = case.rules_tested 列出的条款（强制判 pass/fail，禁止 n/a）
     ∪ 其余条款中 judge 判定在本文本情境下适用的条款（判 pass/fail）
分子 = 分母里判 pass 的条款数
总分 = 分子 / 分母
```

- `rules_tested` 之外、judge 判定不适用的条款记 `n/a`，不进分母也不进分子。
- 因为 `rules_tested` 部分对基线版和带 skill 版是同一个集合，两版分母永远有相同的
  强制下限，通过率具备可比性；自由裁量部分允许两版各自浮动，但不影响强制部分的对比。
- `run_evals.py` 对同一 case 分别跑「不带 skill」与「带 skill」两版改造提问，
  用本 rubric 逐条打分后取总分对比。

## 验收线 v2（2026-08-08 起生效）

四条并列，全部满足才算达线；任一条不满足，视为 SKILL.md 规则文本不够可执行，回 SKILL.md
重新打磨措辞后重跑：

1. **逐条款不劣于**：每一个双臂（基线版/带 skill 版）都有分母的条款，带 skill 版通过率
   ≥ 基线版通过率，或者差距 ≤ 1 个案例（即 1/分母，用来容忍 judge 打分噪声，不要求
   严格单调）。
2. **P1 专项**：P1 总通过率 ≥90%，其中 `case_type: "unverified"` 子集的 P1 通过率
   单独 ≥80%（防止 unverified 子集被 verified 子集的高分稀释掩盖）。
3. **总通过率 ≥80% 地板**（继承自 v1）。
4. **"显著高于基线"不再作硬门**：基线差值只做信息披露，写进跑分报告供参考，不参与
   达线判定。
