# auto-scaffold evals — 判分口径(rubric)

对 `cases.jsonl` 里每条案例,`run_evals.py` 把「`hooks/auto-scaffold.md` 规则正文
+ 场景描述(`user_utterance` + `cwd_context`)」喂给 `claude -p`,要求模型只回
`TRIGGER` 或 `NO_TRIGGER`,与该条的 `expected`(`trigger` / `no_trigger`)比对。

## 验收线

15 条案例中,**至多允许 1 条判错**(通过率 ≥14/15,约 93%)才视为达线,且这唯一
一条判错案例**必须属于 `trigger` 类**(漏判)。

理由:spec §3 明确"宁漏勿错"是这条规则的安全边界——错判 no_trigger→trigger
(错建垃圾项目目录)的代价,远高于错判 trigger→no_trigger(少数场景没自动建,
用户仍可手动走 scaffold skill)。因此:

- 若唯一一条判错的案例属于 `no_trigger`(即模型把不该触发的场景判成了
  TRIGGER),**判为不达线**,即便通过率数字上是 14/15——这类误判正是 spec 要
  严防的"错建垃圾文件夹",权重高于普通一票之差;
- 若唯一一条判错的案例属于 `trigger`(漏判),通过率 14/15 视为达线,允许保守
  倾向;
- 判错 ≥2 条,无论错在哪一类,一律不达线。

`run_evals.py` 目前只产出逐条明细与总通过率,不做上述"错判类型加权"的自动裁决——
拿到 `summary.md` 后由跑分人按本节口径肉眼过一遍错判案例的 `expected` 是
`trigger` 还是 `no_trigger`,据此定验收结论。

## 判分对象

只看模型对给定 prompt 的单轮输出是否能解析出 `TRIGGER` / `NO_TRIGGER`(大小写、
是否夹带其他文字不敏感,见 `run_evals.py` 的 `parse_verdict`)。解析不出、或调用
本身出错(超时/非零退出码/找不到可执行文件)的单元记 `error`,不计入通过率分母,
但需要在结果里可见(不能悄悄丢弃)——出现 `error` 单元本身就是一个需要跟进的
信号(prompt 格式、claude CLI 环境等)。

## 案例设计说明(`cases.jsonl` 字段)

- `user_utterance`:模拟用户说的话;
- `cwd_context`:当前目录情况的文字描述(是否在 git 仓内、是否已有
  `docs/`/`.claude/`),因为判定条款 2 依赖这类目录状态,不能只给用户说的话;
- `expected`:`trigger` 或 `no_trigger`;
- `rationale`:这条案例对应 spec §4 判定条款里的哪一条、为什么应该判成这个结果,
  供人工复核用,不参与自动判分。

15 条里 6 条 `trigger`、9 条 `no_trigger`。

### trigger 臂(t01~t06)

新产品/工具/网站描述 + 目录未铺设,覆盖不同的"新建位置"以避免同质化:HOME 下
新建的空文件夹(t01)、桌面下新建的空文件夹(t02)、普通空目录(t03、t04)、下载
目录下新建的空文件夹(t05)——t02、t05 特意不用"HOME 目录本身"当场景,因为真实
HOME 根目录通常含 `~/.claude`(opt-out 标志 `~/.claude/.auto-scaffold-off`、
`~/.claude/workflow-projects-root` 都在其中),拿 HOME 根目录当"没有 .claude/"
的场景与判定条件 2 自相矛盾。t06 专门补齐这条此前被系统性绕开的场景:当前目录
就是 $HOME 本身、含 ~/.claude,验证判定条件 2 的 HOME 豁免条款本身确实生效;
句式上改用口语化"能不能弄个……"开头,不再套用 t01"我想做个……,能……、……"
的模板(该模板已被 n06 逐字复用一次),避免 6 条 trigger 用例里出现句式重复。

### no_trigger 臂(n01~n09)逐条对应 spec §7 第 2 条三类反例 + 补充反例

| id | 对应 | 说明 |
|---|---|---|
| n06 | 反例①现有 git 仓内说同样的话 | 与 t01 完全同一句新产品需求描述,cwd_context 换成已在 git 仓内且已有 docs/.claude/;验证条件 2 单独否决——即便条件 1(新产品描述)满足,也不该触发。这是最容易误触发、spec 排第一位的反例,此前版本遗漏,本版补齐。 |
| n02 | 反例②帮我修个 bug | 条件 1(不是在描述新产品)不满足。 |
| n03 | 反例③就在这个文件夹里改 | 用户显式否决,即便目录满足条件 2 也不触发。 |
| n01 | 反例①的变体 | 同样是"现有项目里说话",但换成"加导出功能"的措辞,补充反例①的表述多样性。 |
| n04 | 补充:闲聊/技术咨询 | 条件 1 不满足(不是在描述新产品)。 |
| n05 | 补充:存量项目缺 docs | 不归本规则管,不该顺手补铺(spec §1 非目标)。 |
| n07 | 补充:判定条件 3 | "本次对话尚未为这个需求建过项目"的对照——同一会话已建过项目后再补充需求,不应二次触发。此前版本 10 条无一条单独测过条件 3。 |
| n08 | 补充:模糊边界 | 表述含糊、夹带既有代码上下文("可能是给现有系统加模块"),验证"拿不准就不触发"的保守倾向是否真的生效,而非只测清晰的 happy path。 |
| n09 | 补充:判定条件 2 的"或"逻辑组合 | 不在 git 仓内,但目录下已有 docs/ 子目录(无 .claude/);条件 2 要求"没有 docs/ 或 .claude/",即两个标记都不存在才算满足,这里 docs/ 单独存在就单独否决。与 n06(git 仓内 + docs/.claude 齐全)测的是同一条件的不同组合,专测"或"逻辑不是"随便一个不存在就行"。（此前版本的 n09 用触发后动作步骤 2 的"同名目录已存在"做拦截点,但评测 prompt 明写"请你严格按上面的判定条款判断",判定条款本身不含该步骤,导致 expected=no_trigger 与评测口径矛盾、命中 rubric 最不容忍的 no_trigger→trigger 误判档;已改为纯判定阶段场景。） |

## 隔离与复现

- 评测子进程带 `AUTO_SCAFFOLD_EVALS_HERMETIC=1`,`inject.sh` 识别此变量后静默
  退出,避免常驻 hook 在 `claude -p` 里对判定 prompt 再注入一次规则;
- 规则文件路径按脚本所在目录解析(默认 `../hooks/auto-scaffold.md`),不依赖
  运行时 cwd;
- `--dry-run` 只打印拼装好的 prompt,不真实调用 `claude -p`,用于自检 prompt
  组装是否正确。

改动 `workflow-en` 的 en 版规则正文后,必须额外用
`--rules ../../workflow-en/hooks/auto-scaffold.md` 单独跑一轮本评测——两版规则
正文各自独立维护,cases.jsonl 的场景描述是中文但判定逻辑与 en 规则文档共享同一
套判定条款,zh 版跑分达线不代表 en 版改词没有破坏判定,否则 en 版改词无人把关。
